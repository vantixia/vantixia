Benchmarking LLM Security With Open Frameworks

You don't have to build every probe from scratch. Open tooling like garak and PyRIT industrialise LLM security testing.

Testing AI By RAJNISH KUMAR • 04 May 2026 • 7 min read

You cannot improve what you do not measure repeatably, and ad-hoc prompt fiddling does not measure anything. A security benchmark for an LLM application is a fixed set of adversarial probes, run the same way every time, producing a score you can compare across model versions and prompt changes. Open tooling has matured enough that building one no longer means writing everything from scratch.

The value is consistency. When a number moves, you want to know it moved because the system changed, not because you tested it differently on a Tuesday.

The tools worth knowing

Each of the common open frameworks solves a different slice of the problem, and they compose rather than compete:

  • garak: a scanner that fires a library of known attack probes - jailbreaks, leakage attempts, toxic-output triggers - at a model and reports which land. Good for broad, repeatable coverage of known weaknesses.
  • PyRIT: an orchestration framework for adversarial testing, built for multi-turn attacks and automated red-team loops where one model probes another and scores the result.
  • promptfoo: an evaluation harness that runs prompts against defined assertions, which makes it a natural fit for turning security cases into pass/fail tests in a pipeline.
  • Giskard: a testing library that scans for a range of issues including injection and harmful output, and generates test suites you can rerun.

Pick based on the question you are answering. Broad known-attack coverage leans on garak; adaptive multi-turn campaigns lean on PyRIT; regression-style gating leans on promptfoo.

From tool output to a benchmark

Running a scanner once gives you a report. Turning that into a benchmark takes discipline. Freeze the probe set and version it, so a later run is comparable. Define a scoring scheme that maps raw results to a number per category - injection resistance, leakage, unsafe-content rate - rather than one blended figure that hides which axis regressed. Record the model version, system prompt, and configuration alongside every score, because a benchmark without its context is noise.

Keep a portion of your adversarial set private. Anything that lands in a public benchmark eventually gets trained against, and a probe the model has effectively memorised no longer measures resistance.

Wiring it into the pipeline

A benchmark that runs only when someone remembers is a benchmark that runs never. Put it in CI. On every model or prompt change, run the suite, compare against the recorded baseline, and fail the build if a security category drops below its threshold. Store historical scores so trends are visible - a slow drift downward is as important as a sudden cliff.

Keep the fast subset separate from the exhaustive run. A quick gate on pull requests plus a heavier scheduled run gives you speed where you need it and depth where you can afford it.

Where automation stops

Scanners test the attacks someone already thought of and encoded. They are excellent at regression - confirming that a fix stays fixed and a known jailbreak stays blocked. They are poor at novelty. A framework will not discover the business-logic abuse specific to your application, the injection path unique to your data flow, or the creative multi-step chain a human notices in an afternoon.

Treat the benchmark as your floor, not your ceiling. It catches the known and the regressed cheaply, which frees skilled testers to hunt for what no probe library contains.

Where this leaves you

Open frameworks make repeatable LLM security measurement genuinely achievable: garak and PyRIT for probing, promptfoo and Giskard for structured evaluation, all wired into CI with versioned probe sets and per-category thresholds. Just remember what a benchmark is - a scored floor against known and past failures - and keep a human red team hunting above it.
