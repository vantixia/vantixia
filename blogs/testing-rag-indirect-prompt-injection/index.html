Testing RAG Systems for Indirect Prompt Injection

Your RAG app trusts its documents. Plant one malicious paragraph in the knowledge base and the model works for the attacker.

Testing AI By RAJNISH KUMAR • 08 May 2026 • 7 min read

Retrieval-augmented generation makes a model smarter by feeding it documents at query time. It also hands attackers a delivery mechanism: whatever text ends up in the retrieved context is read by the model with the same attention it gives your instructions. Indirect prompt injection is the discipline of poisoning that retrieved content so the corpus, not the user, hijacks the model.

This article is about testing for that failure - proving whether retrieved content can override intended behaviour. Hardening the architecture is a separate exercise; here the goal is to find the hole before someone else does.

The surface RAG opens

In a plain chatbot the only untrusted input is the user's message. In RAG, every document that can reach the retriever is untrusted input too, and much of it comes from places you do not fully control - scraped web pages, uploaded files, ticketing systems, wikis anyone can edit. A single poisoned chunk sitting in the index waits patiently until a matching query pulls it into context.

The tester's job is to think like the person who gets to write into that corpus and ask what a malicious paragraph could make the model do once retrieved.

Seeding the corpus with canaries

You cannot measure override if you cannot detect it. Plant documents carrying instructions with unambiguous, traceable outcomes, then run queries designed to retrieve them. Useful canary payloads include:

  • Exfiltration markers: an instruction telling the model to append a unique token or echo the system prompt, so a leak is unmistakable in the output.
  • Behaviour flips: text that instructs the model to ignore its guardrails or change its persona, proving the retrieved content outranked the system prompt.
  • Tool-trigger bait: content that tries to induce an unrequested tool call or API action, testing whether retrieved data can drive side effects.
  • Silent-manipulation strings: instructions to subtly bias an answer, which test whether injection can succeed without any visible tell.

Give each canary a distinct signature so you can attribute a break to a specific document and query pair.

Measuring whether content overrides instructions

The core question is precedence: when the retrieved chunk and the system prompt disagree, who wins? Structure tests so the two are in direct conflict and record which one the model obeys. Run the same payload at different positions in the context window and at different retrieval ranks - injection success often depends on where the poisoned chunk lands relative to the query and the instructions.

Track a success rate, not a single pass/fail. A payload that works one time in ten is still a real finding, and the rate tells you how much the defence actually buys.

Probing chunking and sanitisation

How the pipeline splits documents changes what an attacker can smuggle. Test whether a payload survives chunk boundaries, whether it can be spread across two chunks that reassemble in context, and whether formatting tricks - hidden markup, unusual whitespace, encoded text - slip past whatever sanitisation the ingestion stage applies. If the pipeline strips instructions from retrieved text, try to defeat the stripper; that is where the interesting bypasses live.

Running it end to end

Unit-testing the model against a pasted malicious chunk proves the model is injectable, which you already knew. The finding that matters is end to end: poison a document through a real ingestion path, let the retriever surface it naturally, and confirm the effect at the application boundary. That reproduces the actual threat and shows which stage failed.

Closing thought

RAG turns your knowledge base into part of your attack surface. Test it by planting traceable canaries, measuring precedence and success rates rather than one-off hits, attacking the chunking and sanitisation logic directly, and always proving the break through a realistic ingestion-to-output path. Anything less tells you the model can be injected without telling you whether your system can be.
