Securing the RAG Pipeline: Where Retrieval Meets Risk

Retrieval-augmented generation pulls in documents you don't fully control. Every one of them is an instruction the model might obey.

AI Security By RAJNISH KUMAR • 04 Aug 2026 • 8 min read

Most teams build retrieval-augmented generation the same way: point an ingestion job at a document store, embed everything, wire the top results into a prompt, and ship. It works disturbingly well, which is exactly why nobody stops to ask the security question – you have just built a pipeline that takes content written by people you do not control and feeds it directly into the reasoning process of a model acting on your users' behalf.

A RAG system has five stages – ingest, chunk and embed, store, retrieve, generate – and each hop is a trust boundary that most architecture diagrams leave unmarked. Walk them in order and the risks fall out naturally.

Ingestion: every document source is an input channel

The corpus feels like "our data," but look at who can write to it. Shared wikis, support tickets, uploaded files, mailboxes, public web pages – in most organisations, hundreds of people (plus any outsider who can email in or file a ticket) can insert text into the sources a RAG pipeline drinks from. A document that contains instructions rather than information will eventually be retrieved and placed into the model's context, where it competes with your system prompt for the model's obedience. This is indirect injection with a delivery mechanism you built yourself. During assessments we treat the corpus as attacker-writable by default, and we are rarely wrong.

Countermeasures start at ingest: restrict which sources get indexed, prefer curated repositories over open-write ones, and record provenance metadata – source, author, timestamp – with every chunk, so downstream stages can make trust decisions and incident responders can trace a bad answer back to a specific document.

The vector store is a database – secure it like one

Vector databases tend to escape the scrutiny applied to the relational store sitting next to them. They should not. Embeddings are not encryption: given access to the vectors, meaningful information about the underlying text can be recovered, so a leaked index is a leaked corpus. Apply the boring controls – authentication, network isolation, encryption at rest and in transit – then add the RAG-specific one: enforce document-level authorisation at query time, server-side. If the retrieval layer searches the whole index and filters afterwards in application code, or worse, relies on the model to withhold what the user should not see, then any user can pull any tenant's documents with a well-aimed question. Multi-tenant deployments need namespace or metadata isolation that the store itself enforces.

Retrieval and generation: sanitise what comes back

The retrieval result is untrusted input arriving at the most sensitive moment – prompt assembly. Sanitise chunks before they enter the context: strip active markup, suspicious URLs, and invisible-text tricks, and wrap retrieved content in clear structural markers so it is presented as reference material rather than instructions. None of this makes injection impossible, so constrain the output side too. If the application renders model responses as rich content, a poisoned document can smuggle in a markdown image or link whose URL carries session data – a tidy exfiltration channel that never looks like an attack in your logs. Render conservatively, allow-list link destinations, and require the model to cite which chunks support its answer so unsupported instructions stand out.

Watch the pipeline, not just the prompt

The failures that hurt are the slow ones: a poisoned page indexed weeks before it is ever retrieved, permissions that drifted after a re-index, a new connector quietly added to the ingest job. Log every stage – what was ingested from where, what was retrieved for which query, what the model cited – and periodically re-verify that index contents still match source-of-record permissions. Deleted or de-permissioned documents have a habit of living on in embeddings long after the original was locked down.

Where this leaves you

RAG moves the attack surface from the prompt to the pipeline. The chat window is the last hop; the real perimeter is every system that can write into your corpus, plus the store that serves it. Treat ingestion as untrusted input, the vector database as a crown-jewel datastore, and retrieval results as hostile until sanitised – and your RAG deployment stops being the softest way into your data.
