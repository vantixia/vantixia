Securing AI Agents: When Your Chatbot Can Take Actions

The moment an LLM can call tools, send emails or move money, a prompt becomes a command. Agentic AI turns content risks into action risks.

AI Security By RAJNISH KUMAR • 15 Jul 2026 • 8 min read

A chatbot that can only talk has a limited worst case: it says something wrong. The moment you give that same model tools - a function to send an email, query a database, book a ticket, or run a shell command - the worst case changes shape entirely. Now a sentence in its context window is not just a request; it is a potential command. Agentic AI is where content risk quietly becomes action risk, and where a prompt injection stops being embarrassing and starts being expensive.

The OWASP Top 10 for LLM Applications names this LLM08: Excessive Agency - the risk that a model can do more than the situation actually requires, with more authority than it should hold. Most agent incidents are not exotic. They are ordinary over-permissioning, dressed up in new vocabulary.

The confused deputy, reborn

Security has a decades-old name for the core problem: the confused deputy. A privileged component is tricked by an unprivileged party into misusing its authority. An AI agent is a nearly perfect confused deputy - it holds real credentials, it acts on behalf of a user, and it takes instructions from whatever text lands in its context, including text an attacker planted in a document or web page. The agent is not compromised in any traditional sense. It is doing exactly what it was told, by the wrong person.

Least privilege, applied to tools

The single highest-leverage control is to narrow what the agent can do before you worry about whether it can be tricked. Every tool you expose is attack surface, and every scope you grant is blast radius. Design the toolset the way you would design an API for an untrusted client, because that is what the model is.

  • Minimum tools. Expose only the actions the feature genuinely needs. A summarisation agent does not need a "delete record" function within reach.
  • Narrow scopes. Read-only wherever possible; write access constrained to specific resources; credentials scoped per action rather than one god-token shared across everything.
  • Validated arguments. Never let the model produce a free-form parameter that flows straight into a query or command. Validate against allow-lists outside the model.

Gates for the actions that matter

Not every action deserves the same trust. Reading a calendar is cheap to get wrong; wiring money is not. Classify actions by impact and put a human confirmation step in front of the consequential ones - sending funds, deleting data, messaging external parties, changing permissions. The confirmation must be presented to the real user in a way the model cannot fabricate or auto-approve, or the gate is theatre.

Sandboxing and the paper trail

Assume some injection will eventually succeed and contain what happens next. Run tool execution in a sandbox with no ambient network access it does not need, so a coerced tool call cannot pivot into your internal systems or reach an attacker-controlled endpoint. Then make the whole thing observable: log every tool invocation with its arguments, the context that triggered it, and the outcome. When an agent misbehaves - and one eventually will - that audit trail is the difference between a five-minute rollback and a week-long forensic exercise.

Where this leaves you

Securing an AI agent is not really about the model at all. It is about engineering the space the model acts in: fewer tools, narrower scopes, validated inputs, confirmation gates on real impact, sandboxed execution, and a complete record of what was done. Treat the agent as a capable but gullible insider you cannot fire, and design its permissions accordingly. Do that, and a successful prompt injection becomes an annoyance instead of an incident.
