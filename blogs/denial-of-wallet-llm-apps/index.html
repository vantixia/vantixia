Testing for Denial-of-Wallet: Resource Exhaustion in LLM Apps

You can't DDoS a serverless AI app off the internet - but you can bankrupt it. Denial-of-wallet is model DoS with a billing twist.

Testing AI By RAJNISH KUMAR • 22 Apr 2026 • 6 min read

Most denial-of-service testing asks whether an attacker can take a service down. For LLM applications there is a nastier variant: the attacker keeps the service up and simply makes it ruinously expensive to run. Every token generated costs money, and an application that bills per call to a model provider can be attacked through its own invoice. This is the shape of unbounded consumption that OWASP tracks as a model denial-of-service risk.

The impact here is not downtime, it is spend. That reframing changes what you test for and what "critical" means in the report.

Cost is the impact surface

In a traditional resource-exhaustion test, success looks like a hung server or an exhausted connection pool. In an LLM app, success can look like everything working perfectly while the bill climbs. The service stays responsive; the damage is a five-figure invoice at the end of the month, or a burned-through quota that locks out legitimate users once the budget cap trips.

So the tester's question is not "can I crash it?" but "can I make it spend without limit, and how cheaply on my side?" A single crafted request that costs the attacker nothing but forces expensive generation is a far better exploit than a brute-force flood.

The exhaustion vectors

Consumption attacks come in several flavours, and a thorough test covers each:

  • Token flooding: inputs that force maximal output - asking for exhaustive lists, huge documents, or prompts engineered to defeat length caps and run to the token ceiling.
  • Recursive and agent loops: agents that call themselves or each other, plans that never converge, and reasoning loops that keep spending until something external stops them.
  • Expensive tool calls: prompts that induce repeated or costly downstream actions - external API calls, retrieval over large corpora, or fan-out to multiple sub-requests.
  • Context stuffing: pushing the input toward the maximum context length so every request carries the highest possible per-call cost.

The most damaging findings combine these - a loop that on each iteration issues a maximal generation and an expensive tool call multiplies cost with every cycle.

How to test it

Measure cost, not just latency. Instrument tests to capture tokens consumed and downstream calls made per request, because that is the metric that maps to money. Probe the limits deliberately: does the app cap output length, and can that cap be talked around? Is there a ceiling on how many tool calls one request can trigger? Do agent loops have a hard iteration limit, or do they run until they happen to finish?

Then test the controls that are supposed to contain all this - rate limits per user and per key, token budgets, and spend caps. Try to exceed them, and check whether limits meant for one dimension leave another wide open. A request-per-minute limit does nothing against an attack that spends its budget on a single maximally expensive call.

Mitigations that hold the line

Defence is layered enforcement of hard limits. Cap output tokens per response and total tokens per user session. Bound agent loops with an explicit maximum iteration count and a cost budget that halts the run when exceeded. Rate-limit on cost, not only on request count, so one heavy request is throttled like many light ones. Set provider-side and application-side spend alerts so an anomaly is caught in hours, not on the invoice. Where inputs are large, cap context size before it reaches the model.

The bottom line

Denial-of-wallet is a real class of attack where the payload is your own cloud bill and the service never even flinches. Test it by measuring cost per request, hunting for token floods, unbounded loops, and expensive tool fan-out, and by attacking the caps and rate limits directly. Then enforce hard token, loop, and spend limits - because an LLM app without them is a service that will happily bankrupt itself on command.
