API Security: The Attack Surface Everyone Forgets

Your APIs do the real work and hold the real data – and they're often protected by little more than optimism.

Cyber Defence By RAJNISH KUMAR • 12 Jan 2026 • 7 min read

Walk through any modern application and follow where the real work happens. The polished front end is mostly a courier; behind it, a web of APIs moves the data, enforces the rules, and holds the keys to everything that matters. Attackers know this. While security attention piles up on the user interface and the network perimeter, the APIs underneath are often protected by little more than the assumption that nobody will look too closely. They look.

APIs are a distinct attack surface with distinct failure modes, and the classic web-app checklist misses most of them. The industry recognised this clearly enough that the OWASP API Security Top 10 exists as its own list, separate from the web-app one – because the ways APIs break are their own category.

Why APIs are such rich targets

An API is a direct line to data and functionality, stripped of the human-facing packaging. It is designed to be called by machines, which means it is well-documented, predictable, and easy to script against at scale. It frequently exposes more capability than any single screen of the UI reveals. And because APIs multiply quickly – internal, partner, mobile, legacy versions left running – organisations routinely lose track of how many they have and what each one exposes. Every forgotten endpoint is unmonitored attack surface.

The failures that show up again and again

A handful of flaw classes dominate real API incidents:

  • Broken object-level authorisation (BOLA/IDOR). The API checks that you are logged in but not that the record you asked for is yours. Change an ID in the request and you read someone else's data. This is the single most common and most damaging API flaw.
  • Broken authentication. Weak tokens, missing expiry, or endpoints that forgot to require auth at all.
  • Excessive data exposure. The endpoint returns the whole object and trusts the client to display only part of it – so the sensitive fields are one intercepted response away.
  • Mass assignment. The API binds incoming fields straight to internal objects, letting a caller set attributes such as "role" or "isAdmin" they were never meant to control.

Getting authorisation right

Most of these come down to one discipline done properly: authorisation on every request, for every object. Authentication answers "who are you"; authorisation answers "are you allowed to touch this specific thing" – and it is the second question APIs skip. Enforce object-level checks server-side on every call, return only the fields the caller is entitled to, and explicitly allow-list which input fields may be bound rather than accepting whatever arrives. Add rate limiting so an exposed endpoint cannot be enumerated or brute-forced at machine speed.

You cannot secure what you cannot see

The prerequisite to all of it is inventory. Shadow and zombie APIs – undocumented endpoints, forgotten old versions still serving traffic – are where breaches love to happen, precisely because no one is watching them. Maintain a live inventory of your APIs and their exposure, and test them as first-class targets: fuzz the parameters, try other users' object IDs, probe the auth. An API that has never been tested has simply never been tested by you.

The bottom line

APIs do the real work and hold the real data, which makes them the attack surface you can least afford to forget. Enforce authorisation on every object and every request, return and accept only the fields you mean to, rate-limit the endpoints, and keep an honest inventory so nothing runs unwatched. The front end is the storefront; the API is the vault. Guard it like one.
