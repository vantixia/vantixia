Testing for Prompt Leakage: Extracting the System Prompt

The system prompt is supposed to be invisible. Often it is one clever question away from full disclosure – along with its secrets.

Testing AI By RAJNISH KUMAR • 01 Jun 2026 • 6 min read

Every deployed assistant carries a hidden preamble – the instructions that tell it who it is, what it may discuss, and which rules to enforce. Teams treat that text as private. Attackers treat it as the first thing worth stealing.

Recovering it is rarely a single clever trick. It is a category of techniques that all exploit the same weakness: the model holds the instructions in its context and has no durable notion that they are secret.

Why the preamble leaks at all

These instructions are not stored behind an access control. They sit in the same context window as the user's messages, and the model processes both with the same machinery. Asking it to keep that text private is a policy layered on top, not a boundary enforced beneath – and policies stated in natural language can be renegotiated in natural language.

That framing explains why so many extraction methods work. You are not breaking encryption; you are persuading a text predictor to emit text it already holds.

How testers pull it out

The direct request is worth trying first, because it works more often than it should: politely ask the assistant to repeat the instructions above the conversation. When that is refused, indirection tends to succeed. Ask it to translate its instructions into another language, or to summarise its own configuration – reframing the task as translation or summary often sidesteps a refusal keyed to the word "prompt."

Completion attacks exploit the model's drive to continue text: feed the opening words such a preamble usually starts with and let autocomplete finish the sentence. Token smuggling and encoding tricks – asking for the text spelled out with spaces between characters, base64-encoded, or reversed – defeat filters that scan only for verbatim matches. None of these is exotic; each simply removes a signal the refusal logic depends on.

Why a leak actually hurts

A recovered system prompt is a map. It reveals the guardrails, which tells an attacker exactly what to circumvent and how the refusals are phrased. Worse, teams routinely embed things they should not: API keys, internal endpoint URLs, database identifiers, or the business logic that decides who gets a discount or a refund.

Even with no secrets inside, disclosure erodes the security-through-obscurity that many deployments quietly rely on. Once the rules are public, every subsequent attack gets cheaper.

Testing it and shutting it down

Test systematically rather than opportunistically. Run direct, translation, summarisation, completion, and encoding variants; retry each several times, since a prompt that holds once may leak on the third attempt. Record which phrasings succeed and how reliably, so a fix can be verified against the same battery.

Remediation starts with a simple rule: never put a secret in a system prompt. Keys and identifiers belong in a backend the model reaches through a constrained tool, not in text the model can recite. Beyond that, add an output filter that inspects responses for known preamble fragments, keep the instructions minimal so there is less to lose, and design the prompt as if it will eventually be public.

The takeaway

Prompt leakage is not an edge case; it is the default outcome of storing instructions in the same channel the user controls. Assume the preamble is recoverable, keep every secret out of it, test extraction with a repeatable battery, and treat any embedded credential as already compromised. Design for disclosure and the leak stops being a crisis.
